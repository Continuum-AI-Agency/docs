**What the server tells your assistant:**

> Co-pilot the AI Studio canvas. action=get reads one source: workflow_id for a saved library template, room_id for a real workspace, or the active workspace when neither is supplied; every Canvas read returns room_id. action=build is workspace-first: target='canvas' is the default, requires room_id, and creates a workflow from typed node specs + simple connections. Use explicit target='library' only to save a reusable template. Do not guess node specs: call help_describe \{ tool: 'studio_workflow' \} first for the node_vocabulary field — the 28 node types with their handles, models, sizes and wiring rules. To make the creative for a Planner draft, pass `source_draft_id` instead of hand-written nodes: build reads that draft for its visual prompt and format, seeds prompt → generator (at the format's delivery ratio) → plannerDraft with targetDraftId already set, and writes it into that draft's own workspace. action=workspace_list returns the real Canvas workspaces users see after login; action=workspace_create creates one through the same brand workspace store and returns its room_id + open_url. A brand may hold at most three workspaces: when workspace_create reports CONFLICT, free one with action=workspace_delete \{ room_id \} — a destructive two-phase call that removes the workspace and its canvas, refuses the reserved Planner workspace and refuses the last one standing. action=edit requires an explicit target. target=canvas requires room_id and writes that real workspace; use seed_workflow_id to merge a saved workflow first. target=library requires workflow_id + expected_updated_at and version-guards the saved workflow update. Surgical ops include add_node, remove_node, update_node, connect, disconnect, rewire, attach_library_asset, attach_unsplash_photo, attach_media, detach_media, rename. attach_library_asset accepts the stable `{asset_id,version_id}` returned by library_manage and resolves storage server-side. attach_unsplash_photo `{id, photo_id}` puts an unsplash_search photo on an image node as a hotlinked reference with its photographer credit. action=save writes a named Canvas room back to an existing saved workflow with expected_updated_at; action=save_as_copy explicitly creates a new saved workflow from either room_id or workflow_id. Every mutation returns a read-back graph_hash plus `persisted`: true when everything you asked for landed, false when part of it was refused — a refused part also makes the envelope status 'partial' and names itself in `rejected` (edit) or `unresolved` (build). action=run requires room_id and needs no human at a browser: when a canvas is open ANYWHERE in the brand it runs there, and when none is, the server generates the image/video nodes headlessly and files the media back onto the canvas. With `node_ids`, unrun upstream generators run first, as on the canvas. A scope of action nodes (image.blur, image.crop, …) runs too, one recipe per final action. When PART of the scope needs the browser the rest still runs: the envelope status is 'partial' and `blocked_by` names each skipped node and why. needs_open_canvas is returned only when NOTHING in scope is runnable. run_status resolves the original run's stored room even if the user switches workspaces, and reports `media_refs` and `previews` with the node_id that produced each one. A server-side run is bounded: one run at a time per room (a second call returns status='already_running', started=false, with the in-flight run's handle — nothing new is generated), and at most a handful of generator nodes per call — a wider scope returns status='too_many_nodes' with the cap, so scope it with `node_ids`. Server runs are limited to 10 per brand per clock hour (open-canvas runs do not count); each reports runs_remaining, and a spent budget returns RATE_LIMITED with retry_after_seconds, so batch nodes into one run. action=rename and action=delete manage a saved library workflow (delete is destructive → two-phase). Publisher sinks (plannerDraft/organicPublish/paidPublisher/apiRender) are terminal DELIVERY HANDOFFS: a run never executes them, so get/build/run/run_status report them under `publisher_handoffs` — deliver with the studio_deliver tool. For action=build, target='canvas' writes to the live room the user is viewing (changes appear instantly) while target='library' saves a reusable workflow. The user may be editing the same canvas at the same time, so canvas writes are additive: build adds its nodes alongside whatever is already there, and mode='replace' (build only) is the explicit, destructive opt-in that clears the canvas first. DESTRUCTIVE requests — build mode='replace', and edit with remove_node/disconnect/detach_media — are two-phase: the first call returns status='confirmation_required' with a confirm_token naming exactly what would be removed, and only a repeat of that same call carrying the token executes it. Every other action is additive and needs no token. Returns a structured needs_* result if prerequisites are missing.

**What the server tells your assistant:**

> Deliver a finished AI Studio canvas creative to a terminal destination. studio_workflow builds/runs the graph; studio_deliver carries a DURABLE artifact (Library asset ids) to an exact destination. action=find_targets discovers organic Planner drafts or Meta paid targets to deliver to; omit `format` to see EVERY format (image, carousel and video) and pass it only to narrow. Each organic row carries the `id` to pass as `draft_id`, the `expected_updated_at` to hand straight back to preview, `empty` (a Planner placeholder with no content), `blockers` and `deliverable`. action=preview binds a confirm_token to the exact artifact + destination + expected-current state + intent (intent = attach_to_planner \| publish_organic \| replace_paid_creative \| restore_paid_creative). action=attach_to_planner attaches the creative to a Planner draft (stale-write guarded via expected_updated_at). action=replace_paid_creative swaps a Meta ad's creative for a new immutable creative and returns a restore handle; action=restore_paid_creative undoes it. action=publish_organic validates then hands off to the canonical publisher. action=status polls a delivery operation_id. Writes are two-phase (preview → confirm) and carry a stable operation_id: an exact retry replays the same receipt, and a provider call that fails without a definitive answer is reported as indeterminate — never advertised safe to blind-retry. ### cad_manage

Uploads STL, DXF, or 3MF files, then transforms, renders, validates, or exports them.

| Contract | Behavior |
| --- | --- |
| Changes things | Yes |
| Listed in your assistant | Always. |
| Role | Operator or higher |
| Needs | An active brand |
| Confirmation | None. The call runs when made. |
| Completion | Returns right away. Longer work continues as a job; read the id in the result. |
| Retry | Retry with the same `idempotency_key` to avoid duplicates. |

**What the server tells your assistant:**

> Upload one self-contained STL, ASCII DXF mesh or 3MF package and finalize verified bytes to queue an owned CAD parse. apply creates immutable mesh-transform, explicit-units, or bounded owned-primitive parameter revisions with baseRevision CAS. render queues a still/orbit scene; export produces unqualified STL/DXF-mesh/3MF-mesh. validate runs revision-scoped manufacturing mesh checks; manufacturing_export refuses blocked geometry and exports qualified mm-normalized mesh. benchmark slices only qualified STL using the controlled offline-fff-pla-0.4-v1 profile and returns actual layer/time/material estimates; process and physical qualification remain false. Every mutation uses requestId replay protection. cancel fences active attempts. Poll cad_query action=job. brandId must match the selected brand. Native DWG, external assemblies, arbitrary scripts, general native parametric edits and physical printer dispatch are unsupported.
